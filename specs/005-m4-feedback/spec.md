# M4 · 反馈与看板 —— 规格（Spec）

**上游**：MVP 产品文档 §10.3（反馈回流）、§12 feedbacks 表、§13 API 清单、§14 验收 #5 #6
**依赖**：M3（对话已跑通，`messages.chunk_ids` / `confidence` 已在记）
**下游**：M5 付费（看板的「收入」这一格要它填）

---

## 1. 这一步要证明什么

> **飞轮的第一格齿轮咬合了：粉丝的一次点踩，能变成博主看得见的一条「你这里没讲过」。**

M1~M3 是一条单向流水线：博主给内容 → 粉丝拿回答。
M4 第一次让数据**倒着流回去**。产品规划文档把这叫「飞轮起点」，
而飞轮空转与真转的分水岭是两个数：**盲区关闭率** 和 **二次满意度**。
这两个数在二期才算得出来，但**M4 不把盲区记下来，二期就无从算起**。

所以 M4 的验收不是"有两个按钮能点"，而是：
**一个具体的、博主看得懂、能拿去写下一篇文章的盲区问题列表。**

| 做 | 不做（为什么） |

| 最近盲区问题列表 | 盲区的"已关闭"状态机（要等博主真的补内容，M5 之后） |

## 3. 反馈接口挂在哪 —— 与产品文档的一处偏离

产品文档 §13 写的是 `POST /api/feedback`（全局路径，靠 body 里的 message_id 定位）。

**实现改为 `POST /api/chat/{slug}/feedback`。**

原因是隔离：粉丝**不属于任何租户**。全局路径拿到一个裸的 `message_id`，
后端无从知道该设哪个 `app.current_tenant` —— 要么再开一个
`resolve_message_tenant()` 的 SECURITY DEFINER 口子（RLS 上的第二个洞，
而且这个洞的入参是可枚举的 uuid，比 slug 危险），要么绕过 RLS 查一次。

挂在 slug 下则什么都不用新增：`resolve_share_slug` 已经存在，
slug → tenant_id → `tenantTx`，RLS 全程生效，一个新口子都不开。

> **允许清单原则第 4 次生效：需要开口时，先问"能不能不开"。**

---

## 4. RLS 管不到的那一层

租户隔离保证了「A 租户的粉丝碰不到 B 租户的消息」。
它**保证不了**「张三不能给李四的对话打分」—— 两人在同一个租户下，
RLS 看不出区别。

所以归属校验必须显式写在应用层：

```
feedbacks 写入前，必须 join 到 conversations 并校验
  conversations.fan_user_id = 当前 Cookie 里的匿名身份
```

查不到就返回 404（不是 403）—— 不泄露这条 message_id 是否存在。

## 5. 疑似盲区怎么判

> ⚠️ **本节写完之后被真实模型推翻了一次。** 保留推翻的过程，因为
> 「按文档写、跑一次、发现文档不成立」正是这一步真正的产出。

### 5.1 第一版（错的）：低置信度 **且** 被点踩

产品文档 §10.3 写的是「低置信度 + 负反馈问题，自动标记疑似盲区」。
理由听起来很对：单看点踩不行 —— 回答被踩可能是**风格不像**、**太啰嗦**，
那不是盲区；配上低置信度才说明库里确实没有相关内容。

三层测试全绿。接上真实模型，第一次手动试就漏了：

```
问「港股打新要准备多少现金」
  最高 rerank 分数 0.1163
  → 有切片擦着入口闸门（0.05）过去了 → 模型被调用
  → 模型自己回答「这个他没有讲过。」
  → finish_reason = 'stop'，不是 'no_context'
  → 粉丝看到「他没讲过」就走了，不会再花力气点个踩
  → 看板上：盲区 0
```

同一个专家、同一批切片，答得好的那个问题分数是 **0.8375**。
0.1163 和它根本不是一回事 —— 这是一个教科书级的盲区，一条都没记上。

### 5.2 第二版：**判据只有置信度**

```
疑似盲区(message) = coalesce(confidence, 0) < 0.15
```

- `finish_reason = 'no_context'`（一条都没过闸门）只是低置信度的**极端情况**，
  被这一条包含了，不需要单列。
- **点踩不再参与盲区判定。** 点踩 + 高置信度 = 「有内容但答得不好」，
  那是风格/质量问题，该进**满意度**。混进盲区会让两个数都变得没法用。
- 低置信度**不需要任何人点任何按钮**。规划文档自己写着
  「用户没动机主动反馈 → 隐性反馈」；而检索置信度是全链路里最干净的隐性信号：
  系统自己已经知道库里没料了。

`coalesce(confidence, 0)`：NULL 意味着这次召回压根没打过分，当最低分处理。
**失败往「是盲区」这边倒** —— 误报博主看一眼就划走，漏报是永远发现不了的。

盲区列表里仍然区分两种 `reason`，对博主是同一件事，排查时值得分开看：

| reason | 含义 |
|---|---|
| `no_context` | 一条相关内容都没召回到 |
| `low_confidence` | 擦着入口闸门过去了，但分数很低 |

### 5.3 阈值 0.15 的由来

| 问题 | rerank 最高分 | 库里讲过吗 |
|---|---|---|
| 定投的手续费怎么算 | **0.8375** | 讲过 |
| 港股打新要准备多少现金 | **0.1163** | 没讲过 |
| （M3 另一组）相关 / 无关 | 0.2149~0.2956 / 0.0059 | —— |

0.15 落在两簇之间。**样本很少，这是个占位值**，M6 用黄金问答集校准。

### 5.4 `is_blindspot` 不落库 —— 与产品文档 §12 的第二处偏离

文档把 `is_blindspot` 列在 feedbacks 表里。**实现改为查询时派生。**

§5.1 那次推翻正好说明了为什么：判定规则在**写完当天**就改了一次，
阈值以后还会再改。落库等于**把一个待定的判断冻进历史** ——
改规则那天，新数据按新标准、旧数据按旧标准，同一块看板上两套口径，
而且没有任何地方会报错。派生式则改一处代码，全部历史自动重算。

原始信号（`messages.confidence`、`messages.finish_reason`、`feedbacks.rating`）
全都已经落库且不可变，派生随时可重算，没有信息损失。

等博主真的要「关掉这个盲区」（需要状态）时，那是一张独立的表，不是这一列。

## 6. 看板的四个数

| 数 | 口径 | 现在能算吗 |
|---|---|---|
| 回答数 | `count(messages where role='assistant')` | ✅ |
| 满意度 | `赞 / (赞 + 踩)`，无反馈时为 `null` | ✅ |
| 收入 | —— | ❌ **M5 之前恒为 0** |
| 盲区数 | §5.2 的判定，按 message 去重 | ✅ |

**收入这一格不粉饰。** 现在真实收入就是 0，接口返回 0，
前端明写「M5 接入付费后生效」，不放一个看起来像真数据的 0。

满意度**无反馈时返回 `null` 而不是 0** —— 「没人评价」和「所有人都说不好」
是两件完全相反的事，用同一个 0 表示会把博主吓死。

## 7. 验收标准

| # | 验收 | 怎么算通过 |
|---|---|---|
| F1 | 粉丝能给任一条回答点赞/点踩 | 落库，刷新页面后按钮保持选中状态 |
| F2 | 改主意 | 先赞后踩，库里只有一条记录且是踩 |
| F3 | 点踩可附原因 | `comment` 落库，最多 200 字 |
| F4 | **打不了别人的分** | 伪造 message_id（他人会话）→ 404，库里无新增 |
| F5 | **跨租户打不了分** | A 租户的 message_id 用 B 的 slug 提交 → 404 |
| F6 | 低置信度 → 盲区，**无需任何点击** | 盲区数 +1，`reason` 为 `low_confidence` |
| F7 | 高置信度 + 点踩 → **不是**盲区 | 差评进满意度，盲区数不变 |
| F8 | `no_context` 回答同样无需点击即计入 | 问一个库里没有的问题 → 盲区数 +1 |
| F9 | 看板四个数正确 | 回答数/满意度/收入 0/盲区数 |
| F10 | 满意度无反馈时为 `null` | 前端显示「暂无评价」而非 0% |
| F11 | 盲区列表给的是**问题原文** | 博主能直接看懂"粉丝在问什么我没讲过" |
| F12 | 未登录 / 非本人博主看不到看板 | 401 / 404 |

## 8. 不解决的问题（写下来免得以为解决了）

- **匿名身份可刷**：Cookie 清掉就是新粉丝，可以反复点踩同一条。
  MVP 不做设备指纹 —— 现在的量级下，人工看一眼盲区列表就能发现异常。
- **盲区列表会重复**：十个粉丝问十遍同一个意思的问题 = 十条盲区。
  聚类是 P1（规划文档 §7），二期做。
- **满意度是自选样本**：只有情绪强烈的人才会点。这个数看趋势，不看绝对值。

## 9. 做的时候踩到的（补记）

### 9.1 `meta.message_id` 指向的是空气

M3 的 agent 在 meta 事件里 `uuid4()` 生成 `message_id`，而回答落库时
backend 用 `defaultRandom()` 另生成一个主键。**两个 id 从来没对上过。**

契约上写着「前端拿 `message_id` 用于点赞点踩」，但拿这个 id 去打分必然 404。
M3 没暴露是因为那时没人用它。

改法：backend 在 `beginChat` 时就生成这条回答的主键，随 `POST /internal/chat`
传给 agent，agent 原样回显，落库时用同一个值。**谁落库，谁定主键。**

> **三方各自的单测都发现不了这种 bug** —— 因为两边都在自说自话，各造各的 id。
> 这正是端到端那一层存在的理由（M1 的 `authFetch` 丢请求头是同一类）。

### 9.2 `created_at` 排不出会话内的顺序

`now()` 返回的是**事务开始时间**，同一个事务里插入的两条消息时间戳完全相同，
`ORDER BY created_at` 的结果未定义。

生产上提问和回答分属两个事务，所以一直看起来正常 —— 这种"看起来正常"最危险。
加了 `messages.seq`（bigserial），并把三处依赖时间戳的比较全换掉：
历史排序、`settleChat` 的幂等判断、看板 LATERAL 取"这条回答之前最近的提问"。

顺带发现 `seq` 是全库第一个序列（之前主键全是 uuid），
而 0001 的角色授权只给了表 —— 不补 `GRANT USAGE ON SEQUENCES`，
backend 连一条消息都插不进去。

### 9.3 端到端跑在了旧代码上

一个 12 小时前遗留的 agent 进程一直占着 8000。`scripts/e2e.sh` 新起的那个
绑不上端口默默退出，健康检查却被**旧进程**答应了 —— 连续几轮 e2e 测的都是老代码。

Pydantic 默认忽略多余字段，所以新加的 `message_id` 被老进程静静丢掉，
一点报错都没有，表现成"改了 agent 但行为没变"。

`scripts/e2e.sh` 现在会在端口被占时**直接失败**。
测一个来路不明的构建，比测不成更糟。
