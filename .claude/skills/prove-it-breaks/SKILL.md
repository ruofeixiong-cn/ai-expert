# 先让它坏给自己看

一条没见过它变红的测试，一条没见过它拦住东西的规则，一个没实测过的数字 —— 都不是证据，
是声称。它们最常见的失败方式不是"报错了"，而是**悄悄什么都没做，然后一路绿灯**。

下面是几种让它先坏一次的办法，按代价从低到高。

## 1. 先红后绿

改代码之前先写出能复现的测试，亲眼看它失败，再动手修。

失败信息本身也要看一眼：它描述的是不是你要修的那个问题？
一条因为"语法错误"而红的测试，修完变绿，什么也没证明。

## 2. 修复不在代码里时，临时把它撤掉

配置、数据库权限、基础设施类的修复没法简单地"先写测试" —— 那就反过来：
修完之后，把修复临时改回原样，看测试是不是立刻红，然后恢复。

```bash
# 例：把函数属主改回原来的角色，跑测试，看它红，再改回来
psql -c "ALTER FUNCTION f OWNER TO old_role;"
pytest tests/test_f.py        # 期望：红，且红的原因正是要修的那个
psql -c "ALTER FUNCTION f OWNER TO new_role;"
```

这比"测试通过了"强得多：它证明了**是这个修复在承重**，而不是别的什么东西恰好让它绿。

**恢复现场**：临时改动和验证命令尽量放在同一条命令里，或者立刻跟上恢复的那一步。
中途被打断而留下一个改坏的环境，比不验证更糟。

## 3. 给守门规则造一个探针

新加的 lint、CI 检查、校验逻辑，要造一个它**应该拦住**的东西，确认它真的拦：

```bash
touch protected/dir/__probe.tmp     # 造出违规状态
make check                          # 期望：失败，且报错信息说得清是哪儿违规
rm protected/dir/__probe.tmp        # 立刻清掉
```

守门规则最常见的坏法是"条件写错了，永远为真"。它在 CI 里一直绿，所有人都以为有人在看门。

顺便读一眼它的报错信息：撞上的人能不能据此知道该做什么？

## 4. 在链条里注入失败，看后面还跑不跑

一串检查（`make verify`、CI pipeline、批处理）最危险的地方在于**前面一项失败会让后面的
根本不执行**，而输出看上去只是"有个错"。

验证办法：故意让**第一项**失败（塞一个类型错误、改坏一个配置），确认后面几项照常跑完、
并且最后的汇总正确点名了失败的是哪一项。然后撤掉。

真实事故：`verify: test contract-check typecheck` 这种依赖写法下，`contract-check`
因为产物没提交而失败，`typecheck` 一次都没跑，一个类型错误就这样进了主干。

## 5. 用真实观测代替推断

链条越长，中间环节越容易骗人。能直接观察结果就别从上游推断：

| 想证明的事 | 别只看 | 直接看 |
|---|---|---|
| 用户实际下载了什么 | 构建产物体积表 | 浏览器网络面板里真实请求的文件 |
| 权限改动生效了 | 迁移跑通了 | 换成那个角色真的查一次 |
| 页面还能正常渲染 | 单元测试绿 | 打开它，看清楚不是白屏 |
| 生成器是确定的 | 跑一次没报错 | 连跑两次，diff 为空 |
| 限流生效了 | 代码里有计数 | 并发打 N 次，数结果 |

构建体积表不会告诉你浏览器实际请求了哪几个文件；迁移成功不代表运行时角色看得见数据。

## 6. 报告时，把没验证的说出来

写「已验证」的时候，顺手写清楚**验证了什么、没验证什么**：

> backend 111 / frontend 37 passed；先红后绿验过（撤掉修复后 X 立刻失败）。
> 未验证：真机微信里的表现、需要登录的那两个页面。

这不是免责声明，是给读的人一张准确的地图。写得出"没验证什么"，说明心里清楚边界在哪；
写不出来，通常意味着把"跑过了"当成了"验证过了"。

## 什么时候不必这么做

改错别字、调文案、重命名变量 —— 直接改。

判断标准是**这个东西坏掉的时候会不会悄无声息**。会静默失效的（守门规则、并发、权限、
降级分支、缓存、性能数字）值得花几分钟；坏了立刻就能看见的不值得。
