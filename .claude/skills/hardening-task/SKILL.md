# 加固任务的做法

这个清单已经走过很多轮了。下面每一条都是撞过之后留下的，不是凭空的规矩。

## 1. 开工：同步 main，丢掉旧分支

```bash
git fetch && git switch main && git merge --ff-only origin/main
git diff --stat main <上一个分支>     # 空 = 内容已在 main 里
git branch -D <上一个分支>
git switch -c <新分支名>
```

**为什么是 `git diff` 而不是 `git branch --merged`**：这个仓库用 rebase 方式合并 PR，
合进 main 的提交哈希和分支上的不一样，祖先关系断了 —— `--merged` 和 `--is-ancestor`
都会说"没合并"，而内容其实一模一样。判断依据只看内容差异。

同理，**新分支一定要从 `origin/main` 切**。从旧分支接着写，PR 会把已经合并过的提交
再显示一遍，diff 变得没法看。

## 2. 跨服务就先写 ADR

根 `CLAUDE.md` 的硬约束：一个任务只改一个服务目录，跨界先在 `docs/adr/` 记一条。

判断标准不是"改了几个目录"，而是**这个决定别人以后要不要知道**：新增契约字段、
改数据库角色、改跨服务的状态机 —— 都要。编号顺延，格式照着现有的写：

```
背景（问题是什么，有实测数字更好）
决定（怎么做，为什么这样做）
后果（代价、运维注意、依赖的版本前提）
被否决的方案（写实：包括自己试过、失败了的那些）
```

「被否决的方案」是这些 ADR 里最值钱的部分。ADR-008 里记着"用完成员资格就 REVOKE"
跑不通、以及具体的报错，下次有人想走同一条路会直接省掉半小时。

前端发现接口缺字段时：**不要自己造 mock**，记一条 ADR 然后停下来（ADR-003 就是这么来的）。

## 3. 先让它坏给自己看

改之前先复现，改之后证明修复是承重的。手法和取舍见 `prove-it-breaks` skill —— 那是通用纪律，
这里只说这个仓库里最容易漏的两种：

- **并发问题**：`make test` 全绿不代表没问题，仓库里原来一条并发测试都没有。
  同一操作同时发 N 次，断言结果集（`backend/tests/helpers.ts` 里有现成的造数工具）。
- **依赖本地特权才跑得通的代码**：本地 `app_owner` 曾是超级用户，一整类"绕过 RLS"的代码
  在本地永远是绿的（B27）。涉及数据库权限的改动，用普通角色再跑一遍。

## 4. `make verify` 是完整的门

它会逐项跑 typecheck / contract-check / test / e2e / eval，**跑完全部再汇总**
（以前写成依赖链，一项失败后面的就不跑了，一个类型错误因此进了 main）。
末尾没看到 `✓ verify 全绿` 就是没过。

改了 API schema：跑 `make contract` 并**提交 `contracts/` 的产物**，包括新增的文件。
`contracts/` 全是生成物，手写会被下次生成覆盖。

## 5. 提交与 PR

一个提交只动一个服务目录。中文 conventional commit，正文写**为什么**（问题的症状、
根因、为什么选这个方案），不是罗列改了哪些文件 —— 那些 diff 里都有。结尾：

```
Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
```

提交前确认暂存区里只有这一个服务的东西（`git diff --cached --name-only`）。
之前有一次因为早先 `git add` 过别的目录，前端改动混进了契约提交里。

PR 正文按这个结构写，读的人能在 30 秒内判断要不要细看：

```
## 为什么        —— 症状先行，最好有实测数字/对照表
## 改了什么      —— 决定与取舍，链接 ADR
## 验证          —— 先红后绿的证据 + make verify 的实际数字
## 过程中的发现  —— 原以为 X、实测是 Y（这部分最有价值）
## 还欠着的      —— 没做的、留给人工的、下一步建议
```

## 6. 回写进度

在 `docs/M0-M6回顾与加固计划.md` 的 §9 追加一节：改了什么、测试数字、
以及一张「实现过程中的新发现」表。

**特别要记「我原以为 X，实测是 Y」**：回顾时靠猜列出的受影响范围，真做的时候经常一个都不对
（降权后本以为 agent 种子脚本会红，实测一处都没有）。这类记录是后面判断"猜得准不准"的唯一依据。

顺手把清单里那一条的状态从 ⏸/未做 改成 ✅ + 日期。

## 7. 环境

- **命令找不到先看路径，别以为没装**：`gh` 和 `docker` 在 macOS 上常不在 PATH 里
  （Homebrew 装的 `gh` 一般在 `/opt/homebrew/bin/gh`；Docker Desktop 装成 User 模式时
  CLI 在 `~/.docker/bin/docker`，README 里也写了这一条）。Makefile 会自己找 docker，
  手敲命令时要注意。
- 跑测试前要 `make up`；改了 `infra/postgres/init/` 得 `docker compose down -v` 重建数据卷 ——
  那个脚本只在首次创建卷时执行。
- 浏览器里要登录才能验的（七维页、控制台）留给人做，不要代填密码。
