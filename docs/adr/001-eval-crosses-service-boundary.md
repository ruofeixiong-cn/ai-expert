# ADR-001：评测跑在 agent 里，但要改 backend 的常量

- **状态**：已接受（2026-09-10 首次校准后补充结论）
- **日期**：2026-09-10
- **相关**：`CLAUDE.md`「一个任务只改一个服务目录」、`specs/006-m6-tuning/`

## 背景

M6 的黄金问答集要校准两个阈值：

| 常量 | 在哪 | 管什么 |
|---|---|---|
| `RERANK_MIN_SCORE` = 0.05 | `agent/app/pipeline/config.py` | 入口闸门：哪些切片能进 prompt |
| `BLINDSPOT_CONFIDENCE` = 0.15 | `backend/src/services/feedback.ts` | 看板：哪些回答算疑似盲区 |

两者**量纲相同**（都是 rerank 分数），本来就该用同一批数据一起定。

跑完校准之后结论更强：**它们不只是同量纲，而是应当始终相等** ——
"这些切片够不够格进 prompt" 和 "这个问题库里到底有没有料" 是同一个判断的两个出口。
但评测代码只能住在 `agent/`（它要跑 embedding、rerank、生成，
那是 agent 的职责），于是一次调优必然跨两个服务目录。

## 决定

1. **评测代码全部在 `agent/`。** 不在 backend 里放任何评测逻辑。
2. **`BLINDSPOT_CONFIDENCE` 允许由 agent 的评测结论驱动修改**，
   但改动本身写在 backend，并在 commit 里引用本 ADR 与具体分数。
3. **不把两个常量合并到一处。** 合并的诱惑很大（既同源又同值，"为什么要存两遍"），
   但那要么让 backend 去读 agent 的 Python 文件，要么新开一张配置表 ——
   前者破坏服务边界，后者为两个数字引入一个需要迁移和缓存的新机制。
   两个常量各自留在用它的服务里，靠 ADR 和注释保持同源，代价最小。

## 后果

- 调优类改动天然是跨目录的 commit。**这类 commit 必须带上分数**，
  否则半年后没人知道 0.15 是怎么来的、能不能动。
- 两个常量有漂移风险：改了一个忘了另一个，看板和闸门就会各说各话 ——
  而且不会有任何地方报错。缓解手段是双方注释里互相点名（都写着"应当相等"
  和对方的位置），并在本 ADR 里留下它们同源的事实。
  真出问题时的症状是：博主看到一堆盲区，粉丝那边却答得好好的。
- 若将来第三个服务也需要这个阈值，就该重新考虑第 3 条 ——
  两处靠纪律维持，三处就该上机制了。

## 被否决的方案

- **把评测搬进 backend**：backend 不做 embedding/检索/prompt，
  这是 `CLAUDE.md` 的硬约束，为了少一次跨目录而破坏它不划算。
- **阈值放数据库**：为两个几乎不变的数字引入迁移、缓存、失效逻辑，
  还让"改一个常量"从代码审查变成运行时状态。
