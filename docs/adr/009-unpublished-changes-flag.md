# ADR-009：线上快照是否过期，由 backend 判定

- **状态**：已接受
- **日期**：2026-09-16
- **相关**：`docs/M0-M6回顾与加固计划.md` 的 F01 后半截；
  ADR-003（同样是"前端缺字段就停下来，由后端补"的先例）

## 背景

F01 的前半截已经修了：已上线时会显示「更新线上版本」按钮。
但按钮旁边那句话是**无条件**的 ——「之后的修改不会自动生效，改完点右边的按钮推到线上」。

于是两种相反的情况长得一模一样：

- 博主改完了七维、还没推到线上 → **应该提醒他**；
- 博主什么都没改 → 这句话变成噪音，反复点"上线"只是白白重写一次快照。

上线即快照（`experts.expert_model`），而有效模型 = 逐维度取「确认过的 or 草稿」。
两者是不是一致，**只有 backend 知道**：前端手里根本没有线上快照的内容。

## 决定

`ModelView` 增加一个布尔字段：

```
hasUnpublishedChanges: boolean   // 有效模型与线上快照不一致
```

- 还没上线过（没有快照）时为 `false` —— 那时该显示的是"上线"，不是"有改动没推"。
- 前端据此把提示分成两句：有改动才说「你有修改还没推到线上」，没改动就说「线上是最新的」。

### 为什么不是返回快照时间让前端比

「返回线上快照时间或差异标记」两条路，选后者：

时间戳比不出内容是否真的变了。博主重新确认一个维度、没改任何字，
`updated_at` 照样变新 —— 前端只能得出"有改动"，然后一直提醒他去推一个空更新。
而反过来，**agent 重新生成草稿**也会让时间变新，但未确认维度按「默认通过」进入有效模型，
这时确实变了。时间戳两种情况都分不清，内容比对两种情况都对。

### 怎么比

逐维度比对**规范化后的 JSON**（递归按 key 排序再 stringify）。

两边当前都来自 jsonb，Postgres 本来就会重排 key，直接 `JSON.stringify` 在今天是够用的 ——
但这个前提太脆：任何一处改成在 JS 里拼对象，比对就会开始报假阳性，
而症状是"提示一直在，点了上线也不消失"，很难查。规范化一次就不用再想这件事。

## 后果

- `load()` 要多取一列 `expert_model`（整份快照）。它只在这个读接口里用，
  单个专家的量级是几十 KB，可接受；将来如果嫌大，可以在数据库里存一份快照的哈希。
- 判定是**内容级**的，所以"确认一个维度但一个字都没改"也算改动 ——
  因为 `origin` 这类字段确实会被写进有效模型。这是正确的，不是误报。
- 前端不再无条件唠叨，「更新线上版本」按钮在没有改动时置灰。

## 被否决的方案

- **前端自己比**：前端拿不到线上快照，要拿就得再开一个接口把整份快照传给它 ——
  多一次传输、多一份可能过期的数据，只为算一个布尔值。
- **上线时存一个 `content_hash`**：比存整份快照省，但要多一列、多一处维护，
  而且第一次读旧数据时哈希为空还得回退到内容比对。现在这个量级不值得。
