# ADR-002：构建任务的并发控制与卡死回收

- **状态**：已接受
- **日期**：2026-09-11
- **相关**：`docs/M0-M6回顾与加固计划.md` 的 B06；ADR-001（跨服务常量的先例）；
  根 `CLAUDE.md`「一个任务只改一个服务目录，跨界先记 ADR」

## 背景

B06 是两个问题：

1. **并发写乱**：博主连点两次「构建」，两个 job 并发执行「先删后插」。
   READ COMMITTED 下，第二个事务的 delete 看不到第一个刚提交的行 → 重复切片。
2. **永久卡住**：ARQ 的 `job_timeout` 通过 cancel 实现，任务里抛出的 `CancelledError`
   是 `BaseException`，`except Exception` 接不住 → `build_jobs` 永远停在 running，
   前端进度条永远在转。worker 被 kill 时也一样。

两个问题必须一起设计：一旦加了「同一个专家只能有一个进行中的任务」的约束，
一个永远停在 running 的任务就会**永远挡住后面所有的构建**。

改动横跨两个服务：约束是 DDL（归 backend），写任务状态的是 agent。

## 决定

1. **数据库层保证同一个专家最多只有一个进行中的任务**（backend 迁移）：
   `build_jobs` 上建部分唯一索引
   `build_jobs_one_active_per_expert (expert_id) WHERE status IN ('queued','running')`。
   全量构建和「只重新提炼」都算 —— 两者写的是同一份草稿。
   不用应用层「先查有没有在跑的」：那又是一个 check-then-act，并发下照样两个都过。

2. **agent 入队时撞上索引返回 409**，backend 原样透传给前端（1409，「这个专家正在构建中」）。

3. **卡死回收分三层**：
   - agent 捕获 `CancelledError`（ARQ 超时），把任务标记为失败，再原样抛出；
   - agent 入队前，把该专家「超过 20 分钟没有更新」的进行中任务标记为失败；
   - backend 读取构建状态时，同样的条件对外显示为「已中断」——
     **只读推导，不写库**。`build_jobs` 仍然只有 Python 写：写入方唯一，状态才不会两边打架。

4. **构建任务不自动重试**（ARQ `max_tries = 1`）。重试一个已经被回收（标记失败）的任务，
   会和博主新点的那一次撞上唯一索引。失败了就让博主自己点，错误信息是可读的。

5. **「多久算卡死」两个服务各存一份**：agent 的 `STALE_JOB_SECONDS` 和
   backend 的 `STALE_BUILD_SECONDS`，都是 20 分钟，比 ARQ 的 `job_timeout`（15 分钟）宽裕。
   沿用 ADR-001 的做法：各自留在用它的服务里，注释互相点名。

## 后果

- 迁移会先收掉历史遗留的重复进行中任务，再建索引。
  **生产环境注意**：迁移角色如果不是超级用户，FORCE RLS 会让这条 UPDATE 影响 0 行；
  这时若仍有重复，建索引会失败 —— 这是期望行为（fail fast），需要人工处理。
- 两个 20 分钟有漂移风险。backend 更短时的症状是「前端显示已中断，但点重新构建返回 409」；
  agent 更短时是「点重新构建成功了，但前端还在转」。
- backend 调 agent 的错误翻译新增一条：agent 的 409 透传为 1409，不再一律当成 502。

## 被否决的方案

- **应用层先查再插**：check-then-act，并发下无效。
- **用 Postgres 咨询锁锁住整个构建过程**：锁由 worker 在构建期间持有几分钟。
  它能挡住并发写，但入队那一刻判断不了「有没有在跑」，前端照样会看到两个排队中的任务。
- **agent 起一个定时任务，扫所有租户的卡死任务**：`app_agent` 受 RLS 约束，
  看不到当前租户以外的任何一行；为此开一个 SECURITY DEFINER 口子不值得。
  回收只在有人关心的时候（入队、查看）发生就够了。
