# M0–M6 回顾与加固计划

- **日期**：2026-09-11
- **范围**：M0 地基 → M6 调优（M5 付费未做），前端 / backend / agent 全量
- **状态**：执行中（进度见 §9）
- **一句话**：单用户、串行、网络正常、依赖在线时是对的；在并发、恶意输入、依赖变慢、
  进程被杀、弱网与移动端、会话失效这些条件下，有 50+ 处会出错，其中十余处会直接变成
  安全问题、资损，或者让核心功能用不了。

> 第一版回顾只覆盖了 backend 和 agent，前端是补审的 —— 这本身就是本文要纠正的偏差之一：
> 前端的验收一直只有「类型检查 + 能打包」，所以它被默认成"没什么可审的"。

## 1. 为什么 SDD 流程没拦住

每个里程碑都有 spec / plan / tasks，每个复盘都写了"为什么单测发现不了"——
但这些教训没有回流到 spec 模板里，下一个里程碑照旧只写功能验收。

| # | 原因 | 证据 |
|---|---|---|
| 1 | **验收只有「功能」和「隔离」两个维度** | B1–B11、C1–C11、D1–D11、F1–F12 里，只有 D11 一条涉及中断，没有一条是"同一操作并发两次" |
| 2 | **后端测试全是串行的** | `backend/tests` 与 `agent/tests` 中 `Promise.all` / `asyncio.gather` 出现次数为 0 |
| 3 | **fake provider 让竞态窗口张不开** | 真实模型下"检查额度 → 扣额度"之间隔着几秒生成时间；fake 下只有几毫秒，永远撞不上 |
| 4 | **前端验收只有 `tsc --noEmit` + `vite build`** | S6.5、T5.7、U5.4、V5.6。`frontend/package.json` 没有任何测试运行器 |
| 5 | **浏览器验证是手工抽查正常路径** | M3 复盘第 4 条：Enter 键"用 JS 直接派发 keydown 验证"—— 这恰好绕过了输入法组字，F04 永远测不出来 |
| 6 | **没在手机和微信内置浏览器里测过** | 分享页的真实流量几乎全部来自那里 |
| 7 | **契约只生成了类型，没生成约束** | `ExampleItem.evidenceChunkIds` 要求 `min(1)`，前端"添加一条"给的是 `[]` —— 类型检查通过，运行时必然 400（F03） |
| 8 | **设计承诺没有对账** | 技术方案与代码注释里写了"会做"的，至少 9 处没做（见 §5） |

## 2. 做得好的，要保留

改的时候不要把这些改坏：

- 租户隔离由数据库强制：RLS + `FORCE` + `NULLIF` fail-closed + `WITH CHECK`；agent 角色用允许清单
- 唯一连接入口 + `lint-db-access`；Python 表镜像的漂移测试；`make contract-check`
- 构建"先全部向量化、再单事务先删后插"，失败不留半截数据；提炼失败保留旧草稿
- SSE 边转发边嗅探，结算双层幂等；回答主键由 backend 预生成
- 前端 refresh 单飞（`lib/auth.ts`）；access token 只放内存
- 跨租户一律 404 而非 403；满意度无人评价时为 `null` 而非 0
- 评测驱动调参：阈值扫描与线上共用同一条代码路径

## 3. backend / agent 问题清单

### P0

#### B01 · 链接抓取 SSRF　`agent`

- **位置**：[extract.py:45](../agent/app/pipeline/extract.py#L45)
- **问题**：`from_url` 不校验目标地址，且 `follow_redirects=True`，响应体大小不设上限。
- **后果**：博主粘贴 `http://100.100.100.200/latest/meta-data/...`（阿里云元数据地址），
  agent 在 ECS 上把 RAM 角色的 STS 凭证当正文抓回来入库，博主在素材列表里就能看到。
- **修法**：只允许 http/https；DNS 解析后拒绝私网、回环、链路本地、`100.64.0.0/10` 与元数据地址；
  关闭自动跳转，手动跟随 ≤3 跳且每跳重新校验；流式读取，超过上限立即中止。
- **验收**：对上述地址、以及 302 跳到内网的公网地址，均返回 422 且不发出请求。

#### B02 · 试聊额度可绕过，M5 后即资损　`backend`

- **位置**：[chat.ts:197](../backend/src/services/chat.ts#L197)、[app.ts:267](../backend/src/app.ts#L267)
- **问题**：
  1. 同一 Cookie 并发 10 个请求全部通过 `countUsed < freeTrial`（回答要等生成结束才落库）；
  2. 在 `done` 之前断开，这次不计数，但模型已经调用；
  3. 清掉 Cookie 即得到新匿名身份，试聊无限。
- **根因**：技术方案 §2.2 写的是"开流前预扣、出错退回"，实现成了"事后数回答条数"。
- **修法**：`beginChat` 事务内 `pg_advisory_xact_lock(expert, fan)` 串行化并写入 reserved 记录；
  结算时确认、出错时退回；断开按"已收到第一个 delta 即计费"处理。匿名身份创建按 IP 限流（B09）。
- **验收**：并发 10 个请求、试聊额度为 3 时，恰好 3 个成功、7 个收到 402。

#### B03 · refresh 轮换的两个并发问题　`backend`

- **位置**：[session.ts:95](../backend/src/services/session.ts#L95)
- **问题**：
  1. **令牌链分叉**：两个请求带同一个 token 同时到达，都读到 `usedAt = null`，都签发成功 →
     两条有效链，被盗 token 只要抢在同一时刻使用，就能绕过重放检测；
  2. **多标签页误杀**：前端单飞只在单个标签页内生效。浏览器重启恢复多个标签页时同时刷新，
     后到的被判重放 → 整族吊销 → 用户被踢下线，未保存内容全丢（叠加 F14）。
- **修法**：原子认领 `UPDATE ... SET used_at = now() WHERE id = $1 AND used_at IS NULL RETURNING`；
  10 秒宽限期内的"重放"返回可重试错误码，前端稍候重试一次（此时 Cookie 已是新的）；
  前端再用 `BroadcastChannel` 在标签页之间共享刷新结果。
- **验收**：同一 token 并发 2 次刷新 → 恰好 1 次成功，且不吊销会话。

#### B04 · 嵌套事务可耗死连接池　`backend`

- **位置**：[chat.ts:97](../backend/src/services/chat.ts#L97)
- **问题**：`getChatExpert` 在 `tenantTx` 里又开 `systemTx`，一个请求同时占 2 个连接；池上限 10，
  postgres.js 取连接默认不超时。
- **后果**：10 个粉丝同时打开分享页，每人占 1 个等第 2 个 → 全部挂起。
- **修法**：`users` 无 RLS，直接在同一事务里 join；`lint-db-access` 增加"禁止嵌套事务"规则；
  连接池设置获取超时。
- **验收**：并发 20 个 `GET /api/chat/{slug}` 全部在 2 秒内返回。

#### B05 · 生产环境会用默认密钥启动　`backend` + `agent`（两个任务）

- **位置**：[env.ts:33](../backend/src/env.ts#L33)、[config.py:12](../agent/app/config.py#L12)、[main.py:36](../agent/app/main.py#L36)
- **问题**：`JWT_SECRET` 默认值能通过 `min(16)`；`INTERNAL_TOKEN` 两边默认值相同。
  忘了配置 = 任何人可伪造 JWT。agent 的内部 token 用 `!=` 比较，不是常数时间。
- **修法**：`NODE_ENV=production` 时检测到默认值拒绝启动，agent 同理；agent 改用 `hmac.compare_digest`。

#### B06 · 构建任务并发写乱、会永久卡住　跨服务 → **ADR-002**

- **位置**：[build.py:107](../agent/app/workers/build.py#L107)、[build.py:142](../agent/app/workers/build.py#L142)
- **问题**：
  1. 连点两次"构建"，两个 job 并发"先删后插"。READ COMMITTED 下第二个事务的 delete 看不到
     第一个刚提交的行 → 重复切片；
  2. ARQ 超时通过 cancel 实现，抛出的 `CancelledError` 是 `BaseException`，`except Exception`
     接不住 → `build_jobs` 永远 running，前端永远在转；worker 被 kill 同理。
- **修法**：`build_jobs(expert_id)` 加部分唯一索引 `WHERE status IN ('queued','running')`
  （backend 迁移），重复提交返回 409；写入阶段加 `pg_advisory_xact_lock`；用 `finally` 标记失败；
  running 且 15 分钟未更新 → 判定失败（worker 启动时清理 + 读取侧兜底）。
- **验收**：并发两次构建 → 一个 409；构建中 kill worker → 15 分钟内状态变为 failed 且错误可读。

#### B07 · 超大请求体与事件循环阻塞　`backend` + `agent`（两个任务）

- **位置**：[material.ts:23](../backend/src/schemas/material.ts#L23)、[main.py:92](../agent/app/main.py#L92)
- **问题**：backend 无 `bodyLimit`，`contentBase64` 无长度上限，几百 MB 的 JSON 会被整个读进内存；
  agent 的 `from_file` 与 `trafilatura.extract` 是同步 CPU 活，直接跑在 async handler 里，
  解析大 PDF 期间同进程所有对话流停顿。
- **修法**：素材接口 `bodyLimit` 30MB、其余 64KB；zod 加 `max`；agent 用 `asyncio.to_thread`，
  限制 PDF 页数；解码前先按 base64 长度估算大小。
- **验收**：解析 20MB PDF 期间，另一路对话的首字延迟不受影响。

## 4. 前端问题清单

### P0

#### F01 · 上线之后再也无法"重新上线"　`frontend`

- **位置**：[ModelPage.tsx:156](../frontend/src/features/experts/ModelPage.tsx#L156)
- **问题**：一旦 `shareUrl` 存在，卡片只渲染分享链接，上线按钮所在的分支永远不再出现。
  而同一张卡片的文案写着"改完再点一次上线才生效"，详情页写着"可继续调整后重新上线"。
- **后果**：博主首次上线后的所有修改都无法生效，粉丝永远拿到第一版快照；博主找不到按钮。
- **修法**：已上线时同时显示"更新线上版本"按钮；草稿与线上快照不一致时给出提示
  （需要后端返回线上快照时间或差异标记）。

#### F02 · 博主自己写的条目被标成"AI 推断的"　跨服务 → **ADR-003**

- **位置**：[dimensions.ts:62](../frontend/src/features/experts/dimensions.ts#L62)、[dimensions.ts:65](../frontend/src/features/experts/dimensions.ts#L65)
- **问题**：`emptyItem` 给新条目 `evidenceChunkIds: []`，而 `isEvidenceless` 以"证据为空"判定
  AI 推断。博主亲手添加的条目会被标红："AI 推断的，你的原文里没有这句 —— 请核对或删掉"，
  顶部警告也会把它们计入。"怎么决策"维度的提示恰恰鼓励博主自己补。
- **后果**：M2 最核心的信任界面，把博主本人的输入指认为 AI 编造。
- **修法**：契约里没有区分来源的字段。按根 `CLAUDE.md` 规则，前端**不自行 mock**，
  记 ADR-003"需要后端在 ModelItem 上补 `origin: 'ai' | 'creator'`"，后端补齐后前端按来源渲染。

#### F03 · 确认失败时编辑内容被清空；部分新增必然失败　`frontend`

- **位置**：[DimensionCard.tsx:109](../frontend/src/features/experts/DimensionCard.tsx#L109)、[DimensionCard.tsx:34](../frontend/src/features/experts/DimensionCard.tsx#L34)
- **问题**：点"确认"时先 `onConfirm(draft)` 再立刻 `setDirty(false)`，于是 effect 马上把
  `draft` 重置为服务端的旧数据：
  - 请求进行中，博主的编辑**闪回旧版**，成功后才又出现；
  - 请求失败时，编辑**永久丢失**。
- **必然触发的场景**：契约里 `ExampleItem.evidenceChunkIds` 要求至少 1 条、`ModelItem.content`
  要求非空。博主在"真实样本"里"添加一条"必然 400；在任何维度加了一条还没填的空条目也必然 400
  —— 然后整张卡片的编辑全部消失。
- **修法**：成功回调里再清 `dirty`；提交前按契约约束做前端校验（见 §6.3）；
  "真实样本"的新增要么禁用、要么等 F02 的来源字段落地后放开证据约束（同属 ADR-003）。

#### F04 · 中文输入法回车误发送　`frontend`

- **位置**：[SharePage.tsx:241](../frontend/src/features/chat/SharePage.tsx#L241)、[SharePage.tsx:201](../frontend/src/features/chat/SharePage.tsx#L201)
- **问题**：`onKeyDown` 里 `Enter && !shiftKey` 就发送，没有判断 `isComposing`。
  拼音输入法按回车是"确认候选词"，结果把打了一半的问题发出去，还消耗一次试聊额度。
- **后果**：粉丝端几乎全是中文用户，这是每个人第一次提问就可能撞上的问题。
- **修法**：抽一个 `useEnterToSubmit` hook，统一处理 `e.nativeEvent.isComposing || e.keyCode === 229`；
  点踩原因输入框同样处理。
- **验收**：Playwright 用 CDP `Input.imeSetComposition` 模拟组字，回车不发送。

#### F05 · 分享页一次刷新失败，整页变成"链接无效"　`frontend`

- **位置**：[SharePage.tsx:42](../frontend/src/features/chat/SharePage.tsx#L42)、[SharePage.tsx:98](../frontend/src/features/chat/SharePage.tsx#L98)
- **问题**：`load()` 失败一律 `setNotFound(true)`。每次回答结束都会调用 `load()` 刷新额度，
  这一次请求只要网络抖动，整个对话就被替换成"这个链接无效，或者专家还没有上线"。
  首次加载遇到 500 或断网也显示同一句话，而且没有重试入口。
- **修法**：区分 404 与其他错误；刷新额度失败只静默保留旧值；首屏失败给出"重试"。

#### F06 · 退出登录不清查询缓存，换账号能看到上一个账号的数据　`frontend`

- **位置**：[App.tsx:13](../frontend/src/App.tsx#L13)、[auth.ts:69](../frontend/src/lib/auth.ts#L69)
- **问题**：`QueryClient` 是模块级单例，`logout()` 只清 token。另一个账号在同一浏览器登录后，
  专家列表在 `staleTime` 内直接使用上一个账号的缓存；点进详情还能看到缓存的专家信息。
- **后果**：共用电脑时，前端层面的跨账号数据暴露（数据库隔离没问题，是前端缓存漏了）。
- **修法**：登出、登录、刷新失败时都执行 `queryClient.clear()`；query key 带上 `userId`。

### 新发现 · B27（P0，已修 2026-09-16）：生产环境的分享链接可能全部 404

做 B06 时核实数据库角色，发现：

```
app_owner   rolsuper = t   rolbypassrls = t     ← docker 的 POSTGRES_USER
resolve_share_slug 的属主 = app_owner
```

`resolve_share_slug` 是 `SECURITY DEFINER`，以属主身份读 `experts` 表，而 `experts` 开了
`FORCE ROW LEVEL SECURITY`。它在本地能工作，**只是因为本地的属主是超级用户**，
超级用户连 FORCE 也能绕过。

生产环境（RDS）的迁移账号通常不是真正的超级用户、也没有 BYPASSRLS。那时这个函数在
没有租户上下文的情况下读 `experts` → FORCE RLS 生效 → 0 行 → **所有分享链接 404**，
而接口、日志、测试都不会有任何异常。

**这是一个测试环境保真度的问题**：本地的 owner 权限比生产大，于是有一整类
「依赖 owner 绕过 RLS」的代码在本地永远是绿的。同一个原因也会让 ADR-002 迁移里的
数据清理 UPDATE 在生产上影响 0 行。

修法：见 [ADR-008](adr/008-db-role-fidelity-and-share-lookup.md)，两条都做了，
但第 2 条的「BYPASSRLS 角色」被否决（需要超级用户，托管 RDS 上做不到），
最终用的是限定角色的策略。

### 2026-09-16 · §6.3 契约生成 zod 约束（ADR-007）

`make contract` 增加一步：`openapi.json` → `contracts/public/zod.ts`，
前端提交前的校验不再手抄后端的 `min`/`max`。后端加一条约束，前端自动就有。

**自己写生成器而不是用现成库**：这份 spec 的构造面很窄（41 个组件），
自己生成能保证**遇到不认识的构造就报错**，而不是悄悄降级成 `z.any()` ——
后者等于把"契约即编译期检查"又变回"靠人记得"。生成过程中它真的拦了一次
（`{"type":"null"}`），按设计让 `make contract` 失败，加完支持再过。

**测试**：frontend 新增 7 条，其中一条专门守"条件约束生成不出来、必须前端补"
（`ExampleItem` 的证据按 `origin` 分叉），防止哪天顺手删掉。

**代价**：前端 bundle 347.79 kB → 405.48 kB（gzip 111.05 → 125.67，**+14.6 kB**）。
粉丝在手机上打开分享页也要下载 zod，而分享页根本不用这些校验 ——
F24（路由级代码分割）从"锦上添花"变成了有具体数字的待办。

#### 顺带修掉一个流程漏洞：`make verify` 会掩盖后面的检查

做这一条时发现：F01 那次提交带了一个 backend 的类型错误进 main。

原因不是没跑 `make verify`，而是 **`verify: test e2e eval contract-check typecheck` 这种写法，
任何一项失败 make 立刻停** —— 那次 `contract-check` 因为产物还没提交而失败，
排在它后面的 `typecheck` **一次都没跑**，而输出看上去只是"有个错，提交产物就好"。

改成逐项跑、逐项记、最后汇总，并且快的排前面。已用探针验证：
故意让 `typecheck` 失败，后面四项照常跑完，末尾报 `✗ verify 失败： typecheck`。

这正是 §6 想说的那件事的又一个实例：**教训要变成机制**。
"下次记得重跑一遍"是记不住的，把 Makefile 改成跑完全部才是。
